# 开发工作流

本文件只定义开发推进流程。规则正文以 `references/rule-registry.md` 为唯一来源；触发规则 ID 由 `references/gates.md` 判断。

## 证据顺序

1. 用户当前轮明确要求。
2. 当前项目源码、SQL、配置、命令结果和差异。
3. 项目内已有文档、注释、代码生成痕迹和历史约定。
4. Yudao/ruoyi-vue-pro 通用习惯。
5. 经验推断。

经验推断只能作为线索，不能作为完成证据。证据冲突时，以用户当前要求和真实项目文件为准。

## 任务类型

- 答疑：只解释概念、规则、方案或风险；不默认读项目、不运行命令、不改文件。
- 调研：只读取最小必要证据，定位入口、链路、影响面、已有能力和风险点。
- 开发：修改代码、SQL、配置或页面；必须先写执行清单，并列出触发规则 ID。
- 修复：先定位现象、根因、影响面、最小修复点和触发规则 ID，再改当前切片。
- 验证：执行静态检查、引用扫描或用户授权命令，并记录真实结果。
- 开发文档：把本轮真实证据整理为开发说明、修复记录或交接内容。

## 开发状态机

按“发现 -> 切片 -> 实施 -> 证明 -> 汇报”推进。

1. 发现：复述目标，定位用户角色、入口页面或接口、业务对象、期望结果。
2. 切片：锁定当前最小业务路径，列出本轮覆盖和不覆盖范围。
3. 实施：只修改执行清单允许范围内的文件，保持项目现有风格。
4. 证明：用最低足够成本的验证方式证明改动，无法证明就记录原因。
5. 汇报：说明完成项、验证项、未验证项、无法证明和残余风险。

不要在状态机中加入与本次开发切片无关的阶段。

## 执行清单

非平凡开发或修复前必须写执行清单。小改动可用轻量版，中大改动必须完整。

执行清单至少包含：

- 目标。
- 当前切片。
- 请求范围。
- 允许修改面。
- 禁止修改面。
- 允许文件。
- 禁止文件。
- 越界发现处理方式。
- 越界恢复审批方式。
- 测试文件边界。
- 触发规则 ID。
- 允许验证。
- 禁止验证。
- 评审关注。
- 停止条件。
- 无法证明。

没有执行清单、当前切片、允许范围、测试文件边界或验证边界时，不开始修改业务代码。

## 任务切片

- 小任务：只涉及单页面、单接口、单字段展示、局部校验或局部文案时，使用轻量开发计划。
- 中等任务：涉及 SQL、权限、字典、状态、主子表、前后端契约时，写执行清单并补齐影响面。
- 大任务：跨模块、跨端、复杂状态流、主子表、多接口联动时，先拆成 2 到 5 个开发切片。
- 不确定大小时，按中等任务处理，明确未确认入口和无法证明。

每个切片必须能说清：

- 用户可见目标。
- 入口。
- 数据。
- 动作。
- 结果。
- 允许文件。
- 禁止范围。
- 最小证明。
- 无法证明。

## 切片锁定

- 一个切片只服务一个明确业务结果。
- 同类页面、同类接口、同类状态不要默认批量处理。
- 相邻问题、类似问题、顺手优化只报告，不纳入本轮。
- 当前切片之外的同模式改动需要用户明确批准。
- 发现切片不清、证据不足、风险超过授权范围时停止说明。

## 调研顺序

需要先分析代码再写方案或改代码时，按这个顺序补齐必要证据：

1. 定位功能所在模块、菜单、路由或接口。
2. 找到数据库表、主 DDL、初始化脚本或核心数据来源。
3. 找到后端入口：Controller、Service、Mapper、DO、VO、转换器、错误码。
4. 找到前端入口：API 封装、页面、弹窗、明细组件、字典来源。
5. 搜索同模块和全仓库相似实现，优先找标准写法。
6. 判断本轮属于改字段、改状态、改主子表、改权限、改字典、改导入导出，还是组合修改。
7. 识别风险：事务、并发、状态锁定、历史数据、主子表同步、字段不一致、数据库约束、下游单据。

## 通用链路

默认按这条链路理解和排查：

`SQL -> DO/VO -> Mapper -> Service -> Controller -> 前端 API -> 前端页面`

如果项目结构不同，也沿着“数据定义 -> 后端规则 -> 接口契约 -> 前端使用”的顺序查证据。不要只看一个接口名或一个页面文件就写方案。

## 三段检查

### 编辑前

- 执行清单存在。
- 当前切片、允许修改面、禁止修改面明确。
- 用户可见目标或内部改动原因明确。
- 测试文件边界明确。
- 验证命令上限明确。
- 复用门已做轻量检查。
- 涉及 SQL、接口、权限、字典、状态流、导入导出、错误码或用户提示时，触发规则 ID 已列出。

### 编辑后

- 实际改动文件都在允许范围内。
- 禁止文件没有被修改。
- 当前切片之外的问题只报告，未顺手修改。
- 未创建或修改测试文件，除非用户当前轮明确要求。
- 没有新增无关抽象、清理、重构、脚本或临时文件。
- 触发的规则 ID 有证据或已写入无法证明。

### 交付前

- 已核对差异。
- 已执行允许范围内的验证。
- 生产 Java 改动没有编译证据时，不声称编译通过。
- 用户可见行为有用户视角证据或明确说明未验证。
- 最终回复区分完成、验证、未验证、无法证明和风险。

## 边界审计

当用户询问是否越界、改了哪些文件、为什么改了额外文件、是否有额外操作时，进入边界审计。

边界审计只读：

- 可以查看状态、文件列表、差异和相关证据。
- 不自行编辑、恢复、删除、构建、测试或写文档。
- 发现越界业务文件时，报告文件、原因和建议恢复方式，等待用户明确批准。

## 验证边界

默认可用：

- `git status`。
- `git diff`。
- `git diff --check`。
- `rg` 查引用、契约、权限、字典、字段和调用链。
- 错误码只读扫描。

默认需要用户当前轮授权：

- Maven 编译、打包、安装。
- 前端完整构建或完整类型检查。
- 开发服务器、浏览器运行验证、运行时探测。
- 其他超出本次开发验证边界的高成本或高副作用命令。

如果改了生产 Java 文件但没有用户授权编译或外部成功编译证据，最终只能写“未执行编译，无法证明 Java 编译通过”。

## Codegen 边界

只有用户明确提到代码生成、CRUD scaffold、单表、树表、主子表或模板生成时，才按 Codegen 思路处理。普通业务逻辑修改、字段调整、状态锁定、前后端联调、权限配置，不默认走 Codegen。

进入 Codegen 前先确认：

- 生成类型：单表、树表或主子表。
- 表结构、表注释、关键字段注释。
- 模板或生成器配置。
- 前端类型和输出路径。
- 是否会覆盖已有手写代码。

信息缺失、路径冲突或可能覆盖手写代码时，停止并列出待确认项。

## 交付规则

- “已修改”只对应实际差异。
- “已验证”只对应已执行且有结果的验证。
- “未验证”说明未执行什么。
- “无法证明”说明当前证据不能证明什么。
- “残余风险”说明仍可能影响什么。
- 不把建议、推断、静态阅读或旧记录写成完成事实。

## 方案质量

- 方案只保留最终设计结论，不保留长篇排查过程。
- 计划改动点写落点和逻辑，不贴完整 Java、Vue 或 SQL。
- 新增表方案先写表职责、主从关系、关键字段、状态字段、关联字段、索引/约束建议和 SQL 落点，不默认输出完整建表语句。
- 抽象规则、计算公式、状态判断、权限边界、主子表联动、导入导出口径或异常分支，补 1 组最小示例数据。
- 疑点按规模控制：小改动不写；中等需求最多 1 到 3 条；大需求最多 8 条。
- 疑点必须影响实现方向、数据一致性、权限、状态边界、接口兼容或验证范围，并给出推荐默认处理方式。
