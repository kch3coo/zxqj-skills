# Yudao 测试用例与 Playwright 场景模板

当任务目标是“生成测试用例”“整理测试点”或“给 Playwright 梳理自动化场景”时，默认用这份模板。  
这份模板同时兼顾：

- 测试同学直接阅读和执行
- 后续自动化脚本按结构化场景继续展开

默认原则：

- 先确认模块逻辑，再生成测试用例
- 先出人工可读测试用例，再出 Playwright 场景清单
- 默认不要一上来就直接生成整段 Playwright 代码
- 默认只保留可执行的前置条件、步骤、预期结果、优先级和自动化适配判断，不保留推理过程或排查记录

## 模板

```md
# <模块名>测试用例

## 1. 测试范围
- 所属仓库：`backend / frontend / uniapp`
- 所属模块：如 `system / infra / bpm / report / member / custom-business-module`
- 所属业务线：
- 本次覆盖页面 / 接口 / 移动端入口：
- 测试优先级：`P0 / P1 / P2`

## 2. 前置条件
- 账号角色：
- 基础数据：
- 状态前提：
- 是否需要已有上游 / 下游单据：
- 数据准备：
  - 角色账号：
  - 业务基础数据：
  - 单据初始状态：
  - 上游单据：
  - 下游任务 / 单据：
  - 业务主数据 / 数量类数据：

## 3. 核心场景
- 正常新增：
- 正常编辑：
- 正常查看：
- 正常提交 / 审批 / 执行：

## 4. 边界场景
- 必填 / 非必填：
- 状态锁定：
- 主子表联动：
- 下游生成后限制：
- 前后端限制一致性：

## 5. 异常场景
- 非法状态操作：
- 缺少关键数据：
- 重复提交 / 重复执行：
- 后端业务报错提示：

## 6. 回归范围
- 后台页面：
- 后端接口：
- SQL / 状态 / 权限 / 字典 / 菜单：
- 移动端 / 审批 / 设备联动：

## 7. Playwright 场景清单
- case_id:
  case_name:
  priority:
  auto_candidate:
  auto_reason:
  page_entry:
  preconditions:
  test_data:
  steps:
  expected_ui:
  expected_api:
  expected_db_or_status:
  expected_data_change:
  tags:
```

## 推荐写法

- 先把业务流程和状态边界写清，再拆测试点
- 给每个核心场景标记 `P0 / P1 / P2`
- 前置条件要具体到角色账号、基础数据、单据状态、上游 / 下游单据、业务主数据和数量类数据
- 同一个模块至少覆盖正常流程、状态边界、主子表联动、下游单据 / 任务 / 审批影响、前端限制与后端兜底
- Playwright 场景要标记是否适合自动化：`auto_candidate: yes / no`
- 预期结果默认分层写：`expected_ui / expected_api / expected_db_or_status / expected_data_change`
- 如果某个场景不适合自动化，只写清 `auto_candidate: no` 和简短原因，不展开长篇解释

## 不推荐写法

- 只列页面按钮点击，不说明前置条件和状态
- 只测前端，不检查后端业务限制
- 只写手工测试点，不给自动化场景结构
- 不区分优先级，导致核心链路和低风险回归混在一起
- 不说明是否适合自动化，导致依赖扫码、硬件、人工审批的场景被错误自动化
- 直接贴一整段 Playwright 脚本，导致测试同学和 PM 都看不懂
- 把测试用例写成需求分析、排查日志、设计取舍说明或“为什么这样测”的长篇推理

## 测试用例净化规则

输出正式测试用例前，默认做一次净化：

- 删除“为什么要测 / 为什么不测 / 排除理由 / 排查过程”等过程性说明
- 删除代码阅读过程，只保留测试可执行信息
- 把边界判断改写成测试场景，例如“已生成下游单据后禁止编辑”
- 把自动化限制压缩成一句 `auto_reason`
- 如果用户明确要求测试设计说明，再单独输出“测试设计依据”章节
