# Yudao 模块逻辑梳理模板

当任务目标是“梳理某个模块逻辑”时，默认用这份模板。  
这份模板同时兼顾：

- PM / 测试 / 非开发同学的业务理解
- 开发同学的代码落地和联动分析

默认原则：

- 先讲业务，再讲技术
- 先讲流程，再讲代码
- 先让非开发角色看懂，再补开发落地点
- 默认不要贴大段代码
- 默认只保留业务结论、流程结论和规则结论，不保留排查过程、推理痕迹或反向解释

## 模板

```md
# <模块名>逻辑梳理

## 1. 模块定位
- 所属仓库：`backend / frontend / uniapp / simulator / hardware`
- 所属模块：如 `system / infra / bpm / report / member / custom-business-module`
- 所属业务线：
- 主要使用角色：

## 2. 业务视角说明
- 这个模块是做什么的
- 主要解决什么业务问题
- 谁会使用它
- 常见使用场景有哪些

## 3. 页面 / 流程入口
- 后台入口：页面、菜单、弹窗或列表入口
- 移动端入口：如有则写页面路由和任务入口
- 审批 / 任务入口：如有则写 BPM、待办、已办、详情入口

## 4. 核心流程
- 新增流程
- 编辑流程
- 提交 / 审批 / 执行流程
- 下游流转流程

## 5. 关键业务规则
- 什么情况下允许新增 / 编辑 / 删除 / 执行
- 什么情况下禁止操作
- 常见锁定状态有哪些
- 前端限制和后端限制分别在哪

## 6. 上下游关系
- 上游来源模块
- 下游去向模块
- 是否影响数量类数据、任务、审批、设备、移动端等链路

## 7. 技术链路
- SQL / 表结构入口
- 后端入口：`Controller -> Service -> Mapper / DAL -> DO / VO`
- 前端入口：`api -> views -> components`
- 移动端入口：页面 -> 接口
- 相似实现参考：至少 1 个

## 8. 测试关注点
- 正常流程
- 状态边界
- 主子表联动
- 下游生成后限制
- 前后端一致性

## 9. 测试重点摘要
- 本模块最容易出错的 3 到 5 个点
- 最需要优先回归的链路
- 必须覆盖的状态边界
- 是否存在不适合自动化的场景，例如扫码、硬件、人工审批、外部设备联动

## 10. 风险与待确认
- 当前已确认的点
- 仍待确认的点
- 哪些地方如果没继续查，结论只能算阶段性
```

## 推荐写法

- 先用业务语言讲流程，再补技术链路
- 入口处优先写页面、菜单、任务、审批，而不是一上来就写类名
- 技术链路部分可以写文件路径、类名、方法名，但默认不要贴完整代码
- 如果需要说明历史原因或设计取舍，压缩到“风险与待确认”，不要放在核心流程和关键规则里

## 不推荐写法

- 一上来就只写 `Controller -> Service -> Mapper`
- 从头到尾都只写代码结构，不解释业务含义
- 大段贴现有 Java / Vue / SQL 代码
- PM / 测试看完后仍然不知道这个模块到底是干什么的
- 把模块梳理写成排查记录、思考过程或“为什么不采用某方案”的反向说明
